# 决策记录 0003：含数字键的 LAYOUT 标记不剥离（已知缺陷，暂不修）

Status: proposed
Class: bug-fix

## Problem

`stripRichText`（`src/utils/text.ts`）是**纯文本的唯一出口**——凡是要把游戏标记文本变成纯文本的地方
都走它。它的标记词法在 `src/utils/gameMarkup.ts` 的 `tokenizeGameText`（单一事实源）。

其中 LAYOUT 类标记的键名匹配是 `LAYOUT_[A-Z]+#`，**跨不过数字**。于是含数字的键
（真实存在，例如 `{LAYOUT_PS5#O}`）不被识别为标记，**原样漏进纯文本输出**。

这条缺陷此前只记录在 `src/utils/text.ts` 的文件头注释里——**没有任何文档落点**。
一旦有人重写那个注释块、或只看 Markdown 就动手，这条「已知但故意不修」的判断就会丢失，
下一个人会重新发现同一个问题并重新决定一次（或者更糟：以为它已经修好了）。

## Proposal

**保持现状，但把判断写下来**：

- 不修正则。含数字键的 LAYOUT 标记当前**在真实数据里极少出现**，漏洗的结果多是**无害残留**
  （屏幕上多一段 `{}` 包围的占位文本），而改动面大于收益。
- 真正要修时，做法是把 `LAYOUT_[A-Z]+#` 的字符类扩为 `[A-Z0-9]+`，并补一条用例
  （`{LAYOUT_PS5#O}` 应被剥离）。
- 在 `src/utils/text.ts` 的注释里保留「这是**锁定现状**、不是遗漏」的措辞，并链接到本记录。

### 与相邻缺陷的区别（不要混为一谈）

- **`{Skill:…}` / `{CAL:…}` 孤立占位历史上一律原样透传**（无对应清洗规则），经 raw 还原继续透传，
  这是**保持字节级既有行为**，与 LAYOUT 的「正则跨不过数字」是两件事。
- **`IconMap` 全名**那条同类问题**已经修好并被测试钉住**（`tests/rich.test.ts`）。

## Alternatives considered

**立即修正则。** 暂不采用：真实数据尚未出现该标记，改动面（词法单一事实源 + 两侧消费方 + 用例）
大于收益。作为「随时可做的小修」留在本记录里。

**在视图层兜底清洗。** 否决：会造成**双份真相**——`stripRichText` 是纯文本的唯一出口，
再在组件里洗一遍，两处规则必然漂移，而且新出现的调用方会漏掉兜底。

**干脆不记录，只留代码注释。** 否决：这正是本条 Problem 描述的失败模式。本项目已经因为
「判断只活在代码里」而丢过信息（逐路由 HTML 三项预载的决策与实测就是被 diff 删掉后
才被抢救成 [0002](../0002-per-route-html-preloads.md) 的）。

## Acceptance criteria

- 想修的时候：`{LAYOUT_PS5#O}` 这类含数字键标记被 `stripRichText` 正确剥离。
- `tests/text.test.ts` 覆盖该分支（现有用例已覆盖 color/IconMap/LAYOUT/BR/残留标签等分支）。
- `npm test` 全绿，且 `src/utils/text.ts` 的注释同步更新（不再声称「不识别」）。

## Risks

- **风险低但会长期存在**：只要不修，纯文本导出（页面标题、复制文本、SEO 描述）就可能带
  `{LAYOUT_PS5#O}` 这类残渣。当前影响面靠「真实数据里极少出现」兜着——**这个前提没有被门禁保护**，
  上游哪天开始大量送这种标记，不会有任何报警。
- 若上游行为变化，应把本条升级为 `implemented/`（修完）或重新评估。
