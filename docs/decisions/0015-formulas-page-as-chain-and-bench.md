# 决策记录 0015：战斗公式页改为「乘区链 + 结算台 + 乘区账目」

Status: implemented

Class: feature

## Problem

`/formulas` 原本是一份静态长文：分七段、每段列条目，公式只写成「基础伤害区 × 增伤区 × 暴击区 …」
这样的名字链。三个问题反复出现：

1. **名字链不含算术。** 读者看到十来个乘区名并列，却不知道每一区在实战里是 ×0.45 还是 ×2.2，
   也不知道「跳过防御区」到底值多少。原文里最有信息量的几个数字（对首领 ×2.2、持秽盾 ×3.16、
   24% 穿透在三种情景下分别值 15.06% / 11.17% / 18.56%）都只出现在正文段落里，读完就散。
2. **四条伤害链的差别藏在段落里。** 常规 / 贯穿 / 属性异常 / 紊乱共享大部分乘区，差别只在两三处；
   用条目文本来表达，读者必须自己把四份清单叠起来比对。
3. **原文的算式在图片里。** 2.0 版导论的公式是配图（`防御区 = 等级基数 /（有效防御 + 等级基数）`
   等），站内只能用文字近似复述，无法参与计算、无法复算。

约束：数据面零外部请求（不能引入公式图床或 MathJax CDN）、不新增依赖（不引 KaTeX/图表库）、
站点视觉语言为「档案标本」（细线框、等宽数字、无圆角卡片/渐变/投影）。

## Decision

页面结构改为「一段读法 + 七段机制」，并在机制内部换用四种表达装置：

- **四条链并排**（`FamilyMatrix`）：每条链把乘区名渲染成指向该区账目的锚点链接，
  两条链的差异项（`防御区` / `贯穿增伤区`）以琥珀色标出；链下方是同数据的**参与矩阵**
  （行 = 乘区，列 = 伤害类型），一眼看出「谁跳过谁」。
- **结算台**（`SettlementBench`）：攻击力、技能倍率、增伤、暴击、防御、抗性、减易伤、
  失衡窗口共十一个滑条，实时算期望伤害与每一道闸的系数。闸条从中心 ×1 起算、按 log₂ 取长度，
  向左是衰减、向右是放大；越过乘区有效范围的读数会被截断并给出提示（教「堆到顶等于零收益」）。
- **乘区账目**（`ZoneLedger` + `ZoneRuler`）：每个乘区一条账目，含主式 + 分支式（暴击/未暴击、
  失衡/未失衡）、有效范围色带、归属事实、易错点。所有乘区统一画在 **0–10 的系数轴**上，
  ×1 是一条贯穿各行位置相同的竖线——横向可比「哪一区能涨、哪一区只会砍」；防御区单独用
  0–1.2（它只减不增）。
- **专题小账**（`DefenseLab` / `DazeLab` / `ShieldLab` / `InterruptLab`）：分别回答
  「24% 穿透 vs 30% 增伤谁值」「失衡窗口有多长」「秽盾把账翻成什么样」「这一下能不能打断」，
  每个都把原文的算例做成可改参数的复算，数值必须与原文逐条对得上。

算术与内容分离：

- 算式写成 **token 序列**（`Expr`：`var` / `num` / `op` / `when` / `grp` / `frac`），
  由 `components/formula/FormulaMath.vue` 渲染（分数用上下两行 + 细分隔线，靠 CSS 排版，不引库）。
  字符串无法表达分式与上下标，也不便让「链」与「区」共用同一份定义。
- 所有乘区系数计算收进 `domain/combatMath.ts`（纯函数、无 Vue），单测 `tests/combatMath.test.ts`
  以原文算例为断言的锚：防御区 0.4545、穿透三情景 15.06/11.17/18.56%、贯穿 ×2.2、秽盾 ×3.16、
  失衡持续 8.61 / 6.42 秒、紊乱倍率的逐格累加。
- 内容单一事实源仍是 `src/data/formulaGuide.ts`（纯数据），页面只负责拼装。

数字口径写在页首提示里：已用游戏数据交叉核对过的（首领基础防御 952.8、异常积蓄阈值
600／2250／3000、五种异常倍率、能量 120、喧响 3000）与仍属实测口径的（穿透/减防叠加顺序、
紊乱系数、失衡恢复速度）分开列出，读者知道哪个可以当数据用。

## Alternatives considered

- **保留静态长文，只在段落里补数字。** 最省事，但解决不了「四链差别要自己叠」和
  「乘区大小要自己心算」这两件事——而这正是原文最有价值的部分。否决。
- **引 KaTeX 渲染公式。** 能把分数排得更好看，但为一个页面引入渲染库与字体（还有离线/体积成本），
  违反「不擅自加依赖」；本站的公式复杂度（一处分式、一处下标记号）用 CSS 足够。否决。
- **每个乘区各画一条独立的 0–max 轴。** 每行更饱满，但失去跨区可比性：看不出「增伤能到 ×6、
  抗性只在 ×0–×2 之间动」这件事。改用统一 0–10 轴 + 防御区单独缩放。否决。
- **结算台用「输入框 + 计算按钮」。** 少一次渲染，但读者不会去点；滑条能边拖边看乘区变化，
  才是这个装置的意义。否决。
- **公式以图片形式落地（截原文配图）。** 数据面零外部请求 + 图片候选链约束下要先把图本地化，
  且图片里的数字无法参与计算、无法被检索。否决。

## Consequences

- 代价：`/formulas` 路由 chunk 从纯静态文本涨到约 81KB（gzip 30.7KB），其中绝大部分是内容数据；
  页面比原来长，且引入 4 个交互装置（需维护其与 `combatMath` 的一致）。
- 收益：读者可以自己复算原文的每个算例；四条链的差别、乘区大小与「有效范围截断」变成可看的东西，
  而不只是可读的文字。
- 遗留缺口：原文中只有配图、没有数值的项（如敌方减防/穿透的收益曲线、安东能量消耗表）
  仍未落地；「特殊乘区（距离衰减）」机制本身未探明，页内只给已知类型与倍数。
- 陷阱（新装置带来的）：滚动容器（`overflow-x: auto`）里的 `.sr-only` 是 `position: absolute`，
  会以静态位置为基准逃出裁剪、把文档宽度撑破（`/formulas` 390px 实测多出 63px）。
  因此所有横向滚动容器都加 `position: relative`，并用 `v-scroll-region` 指令在确实溢出时补
  `tabindex="0"`（axe `scrollable-region-focusable`）。
